PLAN DE IMPLEMENTACION: NUEVO TIPO DE PRODUCTO PERSONALIZADO (TFG)
Fecha: 2026-04-14

============================================================
1) OBJETIVO
============================================================
Implementar un nuevo tipo de producto "custom-personalized" que permita:
- Personalizacion con imagen subida por el cliente.
- Personalizacion con mensaje de texto.
- Pueden ser las dos a la vez o no.
- Compatibilidad con variantes (talla, color u otros atributos).

============================================================
2) HALLAZGOS CRITICOS EN EL ESTADO ACTUAL
============================================================

[ALTO] No se valida stock al anadir al carrito en frontend
- En product-details se llama a cartService.addItem() directamente.
- Riesgo: overselling.

[ALTO] Matching de variantes hardcodeado a color/talla
- En backend, variantMatchesSelection() usa color y talla de forma fija.
- Riesgo: si se crean atributos dinamicos, la seleccion de variante puede fallar.

[ALTO] Carrito sin soporte para personalizacion
- CartItem actual no incluye datos de personalizacion (imagen/mensaje).

[MEDIO-ALTO] Tipo de producto sin contrato cerrado
- type se maneja como string libre en varios puntos.
- En admin no existe opcion custom-personalized.

[MEDIO] Interfaz de variantes demasiado permisiva
- Variant acepta campos dinamicos muy amplios.
- Riesgo de inconsistencias entre frontend, backend y BD.

============================================================
3) PROPUESTA DE IMPLEMENTACION POR FASES
============================================================

FASE 1 - Contrato de dominio (backend + frontend)
Objetivo: introducir el tipo custom-personalized sin romper tipos existentes.

Backend:
- Extender modelo Product para soportar:
  - customization_config: reglas de personalizacion.
  - user_customization: payload de personalizacion.
- Validar valores por defecto:
  - allowImage: true
  - allowText: true
  - maxImageSize: 5MB (5242880)
  - maxTextLength: 200
  - imageFormats: [jpg, jpeg, png, webp]

Frontend:
- Crear tipos fuertes:
  - ProductType = simple | variable | virtual | custom-personalized
  - interfaces para CustomizationConfig y UserCustomization
- Actualizar Product para incluir customization_config y user_customization opcionales.

FASE 2 - Admin: crear/editar producto personalizado
Objetivo: habilitar configuracion del nuevo tipo desde formulario admin.

Cambios:
- Agregar opcion custom-personalized en selector de tipo de producto.
- En product-form.ts, al seleccionar custom-personalized:
  - mostrar tab de variantes (si quieres que tenga variantes).
  - incluir FormGroup customization_config.
- Guardar customization_config en payload create/update.

Configuracion sugerida en admin:
- allowImage (checkbox)
- allowText (checkbox)
- maxImageSize (number)
- maxTextLength (number)
- imageFormats (lista)
- textPlaceholder (string)

FASE 3 - Publico: captura de personalizacion en producto
Objetivo: que cliente suba imagen y/o escriba mensaje antes de comprar.

Cambios:
- En product-details:
  - cargar customization_config del producto.
  - mostrar controles condicionales:
    - input file si allowImage = true
    - textarea si allowText = true
  - validar longitud/formato/tamano antes de addToCart.

Importante:
- Validar en frontend para UX y validar de nuevo en backend por seguridad.

FASE 4 - API de validacion y stock
Objetivo: robustez de negocio antes de pasar al carrito/pedido.

Cambios backend:
- Nuevo endpoint validate-customization.
- Reutilizar validate-stock y obligar su llamada antes de agregar item final.
- Reescribir matching de variante para atributos dinamicos (no solo color/talla):
  - comparar por mapa de atributos seleccionado.

FASE 5 - Carrito y pedido
Objetivo: persistir la personalizacion en la compra.

Cambios frontend:
- Extender CartItem con:
  - customization.uploadedImageUrl
  - customization.customText
  - customization timestamp/opcional metadata

Cambios backend:
- En proceso de pedido, guardar snapshot de personalizacion por item.
- Validar stock + customizacion al confirmar orden.

============================================================
4) CONTRATO API PROPUESTO (RESUMEN)
============================================================

POST /products (custom-personalized)
Body incluye:
- type: custom-personalized
- customization_config
- variantes (opcional, pero requerido si el negocio lo exige)

POST /products/validate-customization
Body:
- product_id
- customization: { uploadedImageUrl, customText }
Response:
- valid: boolean
- errors: string[]

POST /products/validate-stock
Body:
- product_id o product_sku o variant_sku
- selection de atributos + quantity
Response:
- ok, availableStock, reason

============================================================
5) RIESGOS Y MITIGACIONES
============================================================

Riesgo: explosion combinatoria de variantes
- Mitigacion: limite maximo de combinaciones al normalizar.

Riesgo: archivos huerfanos en uploads
- Mitigacion: guardar metadata de upload y proceso de limpieza periodica.

Riesgo: inconsistencia de carrito (localStorage)
- Mitigacion: definir estrategia clara (solo cliente vs sincronizado con servidor).

Riesgo: concurrencia de stock en compras simultaneas
- Mitigacion: validacion final y descuento atomico en backend.

============================================================
6) ORDEN RECOMENDADO DE EJECUCION
============================================================

1. Tipos y modelo (FASE 1)
2. Formulario admin (FASE 2)
3. Pantalla publica de personalizacion (FASE 3)
4. Validaciones backend stock/customizacion (FASE 4)
5. Persistencia en carrito/pedido (FASE 5)

============================================================
7) PREGUNTAS FUNCIONALES QUE DEBES CERRAR
============================================================

- La personalizacion es obligatoria o opcional por producto/variante?
- El texto personalizado tiene moderacion de contenido o solo limite de caracteres?
- La personalizacion incrementa el precio segun reglas fijas o por variante?
- Se permite una sola imagen o multiples por item personalizado?

============================================================
8) CONCLUSION
============================================================
Tu arquitectura actual ya tiene base para variantes y media upload, pero para soportar
productos personalizados de forma robusta necesitas: contrato de datos explicito,
validacion backend estricta, matching de variantes generico y persistencia de
customizacion en carrito/pedido.

Con esto se puede implementar sin romper lo existente y de forma incremental.
